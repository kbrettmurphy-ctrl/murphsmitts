# MurphOS Human Interface Guidelines

**Version:** 1.1
**Status:** Locked
**Last Updated:** June 2026

---

# Why This Exists

MurphOS exists to make every customer interaction feel calm, clear, and intentional.

The interface should never make the customer work harder than necessary. Every screen, page, form, button, and message should respect the customer's time, attention, and trust.

Good interface design is not decoration.

It is customer service.

When MurphOS is working well, customers should not think about the interface. They should simply feel that everything is easy, organized, and exactly where it should be.

---

# First Principles

## Respect Attention

Every interaction has a cost.

Every click.

Every second of waiting.

Every unnecessary word.

Every confusing decision.

Every extra screen.

Every moment of uncertainty.

MurphOS treats the customer's time and attention as valuable resources.

Spend them carefully.

---

## Reduce Friction

Every interface decision should reduce friction.

Friction includes:

* Waiting.
* Searching.
* Guessing.
* Re-reading.
* Re-entering information.
* Making unnecessary decisions.
* Clicking more than necessary.
* Scrolling without clear purpose.

If something adds friction without adding value, it does not belong.

---

## Time Is Part of the Interface

The user experiences time the same way they experience color, typography, and layout.

Waiting is part of the interface.

Fast responses build confidence.

Delays create uncertainty.

Whenever possible, MurphOS should respond immediately, communicate progress clearly, and eliminate unnecessary waiting.

If something cannot be instant, it should at least feel acknowledged.

The user should never wonder whether something worked.

---

## Clarity Before Style

A beautiful interface that confuses the customer has failed.

MurphOS should always prioritize clarity over decoration.

If a design choice makes something harder to understand, remove it.

---

## One Primary Action

Most screens should have one obvious next step.

When multiple actions compete for attention, the interface feels uncertain.

MurphOS should make the primary action clear while keeping secondary actions available but quiet.

---

# Visual Hierarchy

Every page should have a clear visual order.

The customer should immediately understand:

1. What this page is.
2. What matters most.
3. What they can do next.

Only one element should dominate at a time.

If everything is emphasized, nothing is emphasized.

The glove, the customer task, or the key message should always be the focus. The interface should support that focus, never compete with it.

---

# Decision Support & Findability

Important customer decisions should be supported where the customer is making the decision.

Do not make customers hunt for information they need to take the next step.

A customer should not have to wonder:

* What options are available?
* Where do I find this?
* Is this still in stock?
* What happens if I choose this?
* Am I supposed to scroll more?
* Did I miss something?

MurphOS should surface choice-support information at the moment it becomes useful.

Examples include:

* Lace colors near relacing information.
* Lace colors inside or near the service request form.
* Shipping instructions after estimate approval.
* Payment instructions when payment is needed.
* Pickup or drop-off instructions when the order is local.
* Availability status where choices are shown.

Anchor links are useful.

They are not a complete solution by themselves.

A section like `/services/#lace-colors` can help customers reach information quickly, but the interface should still make that information visible or discoverable where the customer naturally needs it.

If a customer has to remember that information exists somewhere else, the interface is making them carry the system in their head.

That is friction.

The system should carry the system.

Humans are busy enough misplacing sunglasses that are already on their face.

---

# Layout & Whitespace

Whitespace is not empty space.

Whitespace gives the interface rhythm, calm, and clarity.

MurphOS should use space intentionally to separate ideas, guide attention, and make content easier to understand.

When a page feels crowded, the first solution should usually be more space, not more borders, boxes, or dividers.

Dense layouts should only be used when density helps the user work faster, such as admin tools.

Customer-facing pages should feel open, calm, and easy to scan.

---

# Typography

Typography should whisper.

It should not shout.

MurphOS uses typography to create calm hierarchy through size, weight, spacing, and placement.

Large text should be used sparingly.

Small, readable, well-spaced text often feels more premium than oversized headings.

Headings should guide.

Body text should explain.

Labels should support.

Typography should never compete with the glove, photography, or primary customer task.

---

# Navigation

Navigation should feel effortless.

It should not literally disappear.

It should be present, clear, and easy to use without demanding attention.

Customers should never wonder where to go next.

Navigation should guide quietly, stay consistent, and avoid unnecessary complexity.

A customer should always be able to understand:

* Where they are.
* Where they can go.
* How to get back.
* What the next logical step is.

Good navigation reduces thinking.

---

# Buttons & Actions

Buttons should invite action.

They should not beg for it.

MurphOS should avoid oversized, overly colorful, or visually aggressive buttons unless the situation truly requires urgency.

Primary buttons should be clear and confident.

Secondary buttons should be available but quieter.

Text links should be used when a full button would add unnecessary visual weight.

Avoid placing multiple visually equal buttons beside each other unless the choices are truly equal.

The customer should never have to decode which action matters most.

---

# Forms

Forms should feel simple, respectful, and purposeful.

Every field should earn its place.

Do not ask for information before it is needed.

Do not ask for the same information twice.

Group related fields together.

Use labels that are clear and human.

Avoid placeholder-only instructions.

Show errors clearly and respectfully.

A form should feel like a guided conversation, not paperwork handed over by a bored government office worker with a grudge against society.

When a customer submits a form, MurphOS should clearly confirm what happened and what happens next.

---

# Choice Inputs

When a customer is choosing between visual options, the interface should show those options visually whenever practical.

A visual choice should not be reduced to a plain dropdown if the visual difference matters.

Good examples include:

* Primary lace color.
* Secondary lace color.
* Glove photo selection.
* For-sale glove photo selection.
* Service options when imagery improves understanding.

For lace colors, a customer should be able to see the color while choosing it.

The best version is a swatch picker.

The acceptable version is a clear link or expandable view placed directly near the color field.

The weak version is a plain dropdown that forces the customer to remember what the color looked like from another section.

Memory-based interfaces are lazy interfaces.

The user already has enough to remember, like passwords, oil change dates, and why they walked into the garage.

---

# Motion

Motion should explain, not entertain.

Animations should be subtle, fast, and purposeful.

Motion can help show:

* Something opened.
* Something closed.
* Something moved.
* Something saved.
* Something changed.

Motion should never delay the user, distract from the task, or exist only to show off.

If removing an animation makes the interface clearer or faster, remove it.

---

# Feedback

MurphOS should always acknowledge user actions.

When a customer clicks, submits, saves, uploads, or changes something, the interface should respond clearly.

Feedback should answer:

* What happened?
* Is something still happening?
* Did it work?
* What happens next?

Feedback can be visual, written, or both.

Silence creates uncertainty.

Uncertainty creates distrust.

---

# Performance

Speed is part of trust.

Customer-facing pages should load quickly, respond smoothly, and avoid unnecessary delay.

Admin tools should be fast enough to support real work without making the user wait on repetitive tasks.

Performance is not only technical.

It is emotional.

A slow interface feels careless.

A fast interface feels competent.

MurphOS should avoid unnecessary loading, repeated work, bloated assets, and avoidable delays.

Information should be available when the user needs it, not after they have already lost patience and started questioning the life choices that brought them to this website.

---

# Accessibility

An interface is not finished until it is usable.

MurphOS should be readable, navigable, and understandable for as many people as possible.

Accessibility is not an optional enhancement.

It is part of craftsmanship.

Text should be legible.

Contrast should be sufficient.

Interactive elements should be easy to tap or click.

Navigation should work without confusion.

Forms should be understandable.

Important information should not rely only on color.

Beauty without usability is unfinished work.

---

# Customer-Facing vs Admin Interfaces

MurphOS serves both customers and internal operations.

These experiences share the same principles but may express them differently.

Customer-facing pages should feel:

* Calm.
* Premium.
* Open.
* Trustworthy.
* Easy to understand.

Admin interfaces should feel:

* Fast.
* Dense when useful.
* Efficient.
* Clear.
* Designed for repeated use.

The public website builds trust.

The admin portal reduces work.

Both should feel intentional.

---

# Language in the Interface

Interface copy should be clear, direct, and human.

Use plain language.

Avoid jargon unless the customer needs the correct term.

Use correct glove terminology.

Murph's Mitts relaces gloves.

It does not restring or restitch them.

When teaching customers, be helpful without sounding annoyed that humans insist on using words incorrectly, even though they absolutely do.

Good interface language should reduce uncertainty and guide the next step.

---

# Empty States

Empty states should never feel broken.

If there is no content to show, MurphOS should explain why and guide the user toward the next useful action.

Examples:

* No orders found.
* No photos uploaded yet.
* No gloves currently available.
* No matching results.

Empty states are opportunities to reassure, not dead ends.

---

# Error States

Errors should be calm, specific, and useful.

Do not blame the user.

Do not show technical details unless they help the user or admin solve the problem.

An error message should explain:

* What went wrong.
* What the user can do next.
* Whether their work was saved or lost.

Errors should reduce panic, not create it.

---

# The MurphOS Standard

MurphOS should feel like the digital version of handing a glove to someone who knows exactly what they are doing.

Calm.

Organized.

Precise.

Respectful.

No wasted motion.

No unnecessary noise.

No confusion disguised as design.

Every interaction should make the customer feel more confident than they felt before.

---

# The Murph Test

Before finalizing any interface decision, ask:

1. Does this respect the customer's time?
2. Does this reduce friction?
3. Does this make the next step clearer?
4. Does this build trust?
5. Does this feel calm?
6. Can this be simpler?
7. Can this be quieter?
8. Does this support the glove, the customer, or the task?
9. Does this surface important information where the customer needs it?
10. Will this still feel appropriate years from now?

If the answer to most of these questions is no, rethink the solution.

---

# Closing Principle

MurphOS is not designed to impress people with the interface.

It is designed to make the interface feel effortless.

The customer should remember the care.

The glove.

The clarity.

The trust.

Not the software.

That is the standard.
